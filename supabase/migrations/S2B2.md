# S2B-2: reemplazos atómicos

Migration propuesta: `20261009120000_s2b2_atomic_replacements.sql`.
**No ejecutada en producción.** Agrega dos RPC SECURITY INVOKER, ejecutables sólo por
service_role. No modifica columnas, estados, índices ni datos existentes.

- `listo_replace_selection`: bloquea event_request y elección activa, compara el ID
  esperado, reemplaza e inserta dentro de una transacción.
- `listo_replace_proposal`: bloquea inquiry y propuesta esperada; comprueba si el usuario
  respondió y valida que la cotización pertenezca a esa inquiry. Reemplaza e inserta juntas.
- Si el INSERT falla, Postgres revierte también el reemplazo. Sin compensación JavaScript.
- No llama a Google ni Resend. La validación del option_token y los requisitos alimentarios
  permanece en el backend. La RPC sólo recibe IDs; provider_name nuevo queda vacío.

## Reintentos y conflictos

El cliente envía el ID de la fila activa que estaba viendo (null si no había), y un UUID
estable para la nueva fila. Repetir exactamente la operación devuelve esa fila si sigue
activa. Un ID reutilizado con otro contenido o una operación posteriormente reemplazada
produce conflicto. Elegir la misma opción / misma cotización ya activa con expectativa
correcta reutiliza la fila existente.

La web conserva el ID interno de selección activa junto con los demás IDs del pedido;
no guarda nuevos datos de Google. Tras conflicto actualiza la selección conocida usando
la respuesta, muestra el error y espera otro clic deliberado: no reemplaza automáticamente.
El panel conserva el UUID de operación mientras el botón siga visible, incluso tras error.
Si se cierra/reabre o recarga después de perder una respuesta, refrescar antes de repetir.
No se implementan recuperaciones generales de S2B-3 ni cambios al email de respuestas.

Páginas viejas sin IDs de operación se rechazan. Planes guardados antes de S2B-2 sin ID de
selección pueden recibir un primer conflicto al intentar cambiar de opción; la respuesta

No asumir que un error de red prueba rollback: puede haberse perdido la respuesta.

## Pruebas locales

```sh
npm run check
npm test
docker run -d --rm --name listo-s2b2-test -e POSTGRES_PASSWORD=local-test postgres:16
# Esperar que Postgres esté listo. Sólo contenedor LOCAL DESECHABLE.
LISTO_S2B_POSTGRES_CONTAINER=listo-s2b2-test npm test
docker stop listo-s2b2-test
```

Los tests recrean bases locales `listo_s2b_test` y `listo_s2b2_test` en el contenedor explícito.
No apuntar a uno compartido ni de producción. Verifican permisos, rollback con fallo
inyectado, carreras entre conexiones, reintentos y conflicto con aceptar/rechazar.
